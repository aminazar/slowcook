# 0.7.5 — Tier-1 UI component tests

> Status: drafted 2026-04-23. Implementation not started.
>
> Parent roadmap: [`roadmap-0.7-to-0.11.md`](./roadmap-0.7-to-0.11.md) §0.7.5.
> Prior testgen design: [`0.7-testgen-two-tier.md`](./0.7-testgen-two-tier.md) — this doc extends tier-1 to cover React components; the two-tier model itself is unchanged.

## Goal

Give brew a ratchet-driver for UI code. Today, tier-1 tests are handler-only. Testgen doesn't emit component tests; brew's `allowed_paths` don't cover `src/components/**`. Result: stories with `ui_behavior` ship API-only (story-006 was the surfacing case — 16 handler tests green, zero UI).

0.7.5 closes this by:
1. Testgen emits tier-1 UI tests (`@testing-library/react` + jsdom) alongside handler tests when the spec has `ui_behavior`.
2. Testgen emits component stubs so tests can collect before the real code lands.
3. Brew's `allowed_paths` extend to `src/components/**` + client-side `src/app/**/*.tsx`.
4. New one-per-repo helpers: `renderWithProviders`, `mockFetch`/`realShapedFetch`, `jest-axe` wiring. Emitted by `slowcook init` (not per-story).

What tier-1 UI catches vs. what defers to tier-2 is already enumerated in the roadmap §0.7.5.

## Scope — the seven touch points

### 1. Helper scaffolding (one-time per repo, via `slowcook init`)

Lives in `@slowcook-ai/stack-ts` as part of `getInitArtifacts()` (the 0.7.0 Phase 1B surface). Adds three new files to fresh inits; `--force` overwrites them if the consumer opts in:

- `tests/helpers/render.tsx` — exports `renderWithProviders(ui, options?)` that wraps `render` from `@testing-library/react` with a mock Next.js router provider, optional query client, optional auth state. Keeps per-test boilerplate small.
- `tests/helpers/mocks/fetch.ts` — exports `mockFetch(routes)` (returns a `vi.fn` mock matching URL patterns to canned responses) and `realShapedFetch(mockFn)` (signature-asserting wrapper analogous to `realShapedCreateClient` — throws if called with wrong arg shape).
- `tests/helpers/a11y.ts` — re-exports `jest-axe`'s `axe` + `toHaveNoViolations` and wires the custom matcher via `expect.extend`. One-liner; centralises the axe setup so individual tests just `import { axe } from "@tests/helpers/a11y"`.

**devDependencies added by stack-ts:** `@testing-library/react`, `@testing-library/jest-dom`, `jest-axe`, `@types/jest-axe`. Stack-ts's `getDefaultPackageJsonPatches()` (or equivalent) handles this.

**vitest environment:** existing consumer configs use `node` (or default). For `.tsx` tests we need `jsdom` or `happy-dom`. Stack-ts's vitest config scaffold should emit `environmentMatchGlobs: [["**/*.test.tsx", "jsdom"]]` so handler tests stay fast on node and UI tests get jsdom only when needed.

### 2. Testgen output shape — UI bundle

Extends the existing bundle format from 0.7.0 Phase 2 (`<test_file>`, `<stub path="...">`, `<helper path="...">`).

New block kinds:
- `<ui_test_file>` — the component test file contents. Single per story; lives at `tests/integration/story-N-ui.test.tsx`.
- `<ui_stub path="src/...">` — component stub(s). Can be multiple per story (page.tsx + feature components).

Parsing logic in `parseTestgenBundle` extends to recognize these new tags; emission logic writes them if absent (or marked `@slowcook-stub`).

**When testgen emits the UI bundle:** if the spec has a non-empty `ui_behavior` block, emit UI test + stub(s). If absent (pure backend story), emit handler bundle only — no change from today.

### 3. Testgen prompt — new UI-shape spec

`TESTGEN_SYSTEM` gets a third shape block (after handler-test and stub shapes). Shape spec covers:

- **Imports pattern:** `render`, `screen`, `fireEvent`, `waitFor` from `@testing-library/react`; `renderWithProviders` + helpers from `@tests/helpers/*`; `vi` from vitest; `axe` from `@tests/helpers/a11y`; the component under test.
- **Test categories to generate (drawn from spec's `ui_behavior` + `acceptance_scenarios`):** conditional rendering, state-machine behavior, event handling, form validation UI, error states, loading states, routing intent, semantic structure. Plus one mandatory `jest-axe` test per component.
- **Assertion style:** `toBeInTheDocument`, `toHaveTextContent`, `toHaveClass`, `toBeDisabled`, `toHaveAccessibleName`. Avoid querying by className; prefer `getByRole`, `getByLabelText`.
- **Mocking convention:** `vi.mocked(global.fetch).mockImplementation(realShapedFetch(mockFetch({ ... })))`. Mirrors the Supabase pattern.
- **Reviewer check language:** carry the same "load-bearing property" callouts used in the helper/stub PR body sections today.

Example shown to the LLM (one full test file for a hypothetical profile-edit story).

### 4. Brew changes

- **`ALLOWED_PATHS`** (in brew's context setup) extends to `src/components/**` and client-side `src/app/**/*.tsx`. Today's list already has `src/app/api/**` + `src/lib/**` + a few others; widen.
- **Brew prompt** gets a conditional addition: *"This story has `ui_behavior`; expect to modify or create React components in `src/components/` and/or client pages under `src/app/**/*.tsx`. Follow the conventions in `.brewing/context.md` → UI section."* Triggered by `ctx.spec.ui_behavior` being non-empty.
- **No change to the ratchet logic** — same green-delta rules; the agent just has more files it's allowed to write.

### 5. Context.md updates (consumer-side — rewo)

Add a **Tier-1 UI** subsection after the existing Tier-1 handler subsection. Documents:

- Where UI tests live (`tests/integration/story-N-ui.test.tsx`).
- Required imports (`renderWithProviders`, `axe`, `mockFetch` + `realShapedFetch`).
- Render pattern + common assertion style.
- Mandatory axe test per component.
- Opt-in fakes (router, auth) via `renderWithProviders` options.

Rewo PR for this is separate from the slowcook release; lands after slowcook 0.7.5 is published.

### 6. Forge-github — no changes expected

Workflows don't change shape. `slowcook brew` already runs `npm test` and ratchets whatever's in the manifest; adding UI tests to the manifest is testgen's job, and brew picks them up automatically.

One open question: does `slowcook-brew.yml` need a `jsdom` environment declaration? I don't think so — vitest reads `vitest.config.ts` from the consumer side, and `environmentMatchGlobs` handles the split.

### 7. Tests for 0.7.5 itself (inside slowcook)

- `parseTestgenBundle` — unit tests for new `<ui_test_file>` and `<ui_stub>` blocks (positive + malformed cases).
- `shouldWriteUiStub` / `shouldWriteUiTestFile` — idempotency tests analogous to existing `shouldWriteStub` / `shouldWriteHelper`.
- A small integration-style test that feeds testgen a mock spec with `ui_behavior` and asserts the bundle output has both handler and UI blocks.

## Open questions

Rendering + solving these during implementation, not blocker on drafting:

1. **Next.js App Router: server vs client components.** Server components can't render in jsdom (they use async + suspend). Policy: testgen emits tests for `"use client"` components only; for server components, coverage is tier-2 (acceptance via Playwright rendering the full page). Testgen detects via heuristic — spec's `ui_behavior` is usually about interactive UI, which is client. If a server component is genuinely what's needed, the LLM output notes `<ui_test_file skip="server-component">` and we defer.

2. **`next/navigation` mocking.** `useRouter`, `usePathname`, `useSearchParams` — the render helper needs to provide these. Approach: `vi.mock("next/navigation", ...)` in `tests/setup.ts` with overridable defaults; tests pass their own router via `renderWithProviders({ router: ... })` if needed.

3. **React 19 + Next 16 compat.** `@testing-library/react` latest works with React 19; confirm versions. `jsdom` handles React 19 fine per community reports.

4. **How aggressive should axe be?** Default rule set catches contrast, ARIA, heading hierarchy. Turns off: colour-contrast on mobile-dark if it false-positives on jsdom's computed styles. Decide during implementation after running it on rewo's existing components.

5. **Stub shape for a page vs. a component.** Page stub: `export default function PlaceholderPage() { throw new Error("@slowcook-stub story-N"); }`. Component stub: same pattern. Testgen emits the set needed; LLM decides based on spec's architectural note.

6. **Helper regeneration on `init --force`.** If a consumer customises `tests/helpers/render.tsx`, a future `init --force` would clobber it. Mitigation: the emitted helpers have a `// @slowcook-one-time-scaffold` marker on line 1; `init --force` only overwrites files with that marker still present. Matches the `@slowcook-stub` pattern.

## Sequencing within 0.7.5

Land in this order to keep each step shippable standalone:

1. **Phase A — helper scaffolding in stack-ts.** New init artifacts + new devDeps. Ship as `stack-ts@0.7.5`. Rewo adopts via `slowcook init --force` in a dedicated PR.

2. **Phase B — testgen bundle extension.** Parser accepts new blocks; emission logic writes them. Covered by unit tests. Prompt updated. Ships as `cli@0.7.5`.

3. **Phase C — brew `allowed_paths` + prompt.** Small change. Covered by existing brew tests + a new one. Ships in same `cli@0.7.5`.

4. **Phase D — rewo adoption.** Separate rewo PR: run `slowcook init --force` to get new helpers; update `.brewing/context.md` with the Tier-1 UI subsection; bump `slowcook-cli-version` to `0.7.5`.

5. **Phase E — end-to-end demo.** Re-run testgen on rewo story-006 (currently has only handler tests); confirm it emits the UI bundle; run brew on a hypothetical "new UI-only story" (or delete story-006's hand-written components and let brew rebuild). Budget ~$3-5 of Anthropic spend.

## Definition of done

- Fresh `slowcook init` on a new consumer produces a repo where a tier-1 UI test file can be written by hand and runs cleanly via `npm test`.
- Refreshing testgen on rewo story-006 emits `tests/integration/story-006-ui.test.tsx` with ≥6 test cases covering `ui_behavior`'s acceptance scenarios + an axe test.
- A brew run against a UI-only story (test-manifest contains only UI tests) produces a working component in `src/app/` or `src/components/`, turns the UI tests green, passes the existing handler tests unchanged.
- 114+ cli tests still green; new tests added for the UI bundle parser + helper emission.
- Context.md in rewo documents the new conventions; a contributor reading it can write a new UI tier-1 test without asking questions.

## Risks

- **jsdom's layout engine is approximate.** Some interactions (sheet transitions, focus trapping, `scrollIntoView`) don't match real browsers. For those, tier-1 has to either assert on state/attributes rather than visual effect, or defer to tier-2. Flag in context.md.
- **Helper API churn across versions.** If `renderWithProviders`'s signature changes in 0.8+, existing tests break. Mitigation: version the helper module (`renderWithProviders` takes an options object from day one; add fields over time without breaking callers).
- **Testgen's LLM over-specifying UI behavior.** Vision of what a good UI tier-1 test looks like vs. reality: early runs may produce tests that query by text that's actually an aria-label, or assert on class names instead of semantic roles. Mitigation: strong `TESTGEN_SYSTEM` prompt + concrete example + iteration on the prompt as we see bad outputs.
- **Vitest environment switch cost.** `jsdom` is heavier than `node`; tests pay ~30ms setup per jsdom test file. Mitigation: scope `jsdom` to `.tsx` tests only via `environmentMatchGlobs`. Handler tests stay in `node`.
