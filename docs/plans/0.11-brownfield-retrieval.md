# 0.11 — Brownfield retrieval architecture

> Status: drafted 2026-04-25. Sub-plan of the 0.11 brownfield cooker (see `roadmap-0.7-to-0.11.md` §0.11.0). Implementation will likely span 0.11.x point releases; the brownfield bootstrap command itself can ship before the embedding fallback layer.
>
> Origin: dogfood session 2026-04-24 surfaced 13 brew/refine findings; question came up whether RAG / vector DB is needed for retrieval at scale. Honest answer is "RAG is one tool in a layered retrieval stack; it's the last layer to fire, not the first." This doc captures the architecture so brownfield work doesn't reach for RAG-first by default.

## Why this exists

`code-map.json` + `manifest.json` + `context.md` work fine for greenfield (rewo-scale: ~50 source files). At brownfield scale they break in different ways:

| Project size | What breaks |
|---|---|
| 100–500 files | Nothing yet — same approach scales |
| 500–5K files | Whole code-map can't sit in every iteration prompt; agent needs to query subsets |
| 5K–50K files | Pattern discovery dominates — "where do we already do RLS?" can't be a grep when there are 80 implementations |
| >50K / multi-language / monorepo | Even file paths don't fit; need real retrieval infrastructure |

The default response in industry is "add a vector DB and embed the codebase." That works but:

1. RAG is wasteful for queries that lexical / structural / symbol-aware search would answer for free.
2. RAG has carrying cost — embedding inference, vector store hosting, re-index on commit, model versioning.
3. RAG isn't load-bearing today — none of the rewo brew halts (AGENT_STALLED, ITER_CAP, MANIFEST_DRIFT, tests-green trap, wrong-target work) were fixed by "the agent couldn't find a known-existing pattern."

So the architecture is **layered retrieval** with RAG as the deepest fallback, not the entry point. This doc specifies the layers and the file-based vector store shape.

## Architecture — five layers, cheapest first

The agent (refine / testgen / brew) gets a retrieval API. Each query routes through layers in order; later layers are only consulted if earlier ones return empty or insufficient.

### Layer 1 — Lexical (already available)

`grep` / `ripgrep` via the `Bash` tool. Free, instant, exact. Wins for "find function `foo`" / "where is variable `bearer` set."

No new infrastructure. Agent already has this. Document explicitly so the agent reaches for it first.

### Layer 2 — Symbol-aware

New tools exposed to the agent, backed by `ts-morph` (already in slowcook's dep tree):

- `find_references(symbol)` — every call site of an exported function / type
- `find_implementations(interface)` — every class implementing an interface
- `find_definition(symbol)` — go-to-definition

Cheap (parses the project's TS once, caches) and precise. Wins for "where is this called?" / "what implements this interface?"

Implementation lives in `@slowcook-ai/cli` or a new `@slowcook-ai/retrieve` package. Tools surface via the agent's tool-use schema.

### Layer 3 — Structural (extend existing code-map + cross-brew provenance)

Today's `code-map.json` lists routes / pages / components / helpers / types — file-level shape only. Brownfield needs three additions:

- **Cross-brew provenance index.** Across stories, the same surface area gets touched repeatedly (e.g., story-005 created `MemberReactionsPage`, story-010 attempted a fix, story-011 amended it; an avatar story would touch it again). Without memory, each brew rediscovers the wiring cold and often re-makes earlier mistakes. Stored in `.brewing/provenance.json`, indexed by entity (file / symbol / route), not by brew event. See dedicated section below.
- **Function-signature enrichment.** Each exported symbol gains its signature + caller count + file:line. Example entry:
  ```json
  {
    "kind": "helper",
    "file": "src/lib/data/members.ts",
    "exports": [
      {
        "name": "getProfileByHandle",
        "signature": "(handle: string) => Promise<Profile | null>",
        "callers": 3,
        "line": 42
      }
    ]
  }
  ```
  Without signatures, the agent sees "this file exists" but can't tell whether `getProfileByHandle` is the helper it needs. Signatures + caller counts surface "this exists, X places use it" so duplicating is visibly wrong.
- **Lazy code-map**: per iteration, derive the relevant subset by walking from the target test → its imports → their imports (depth-bounded). Inject ~2–5 KB instead of the whole map.
- **Reverse-dependency graph**: "what imports this file?" Built by inverting the existing import edges in code-map.
- **Test → impl crossreference**: "what tests fail when I touch this file?" Built from manifest + import graph.

Wins for "what's the blast radius of this change?" / "what will break if I change this helper?" / "is there already a helper that does what I'm about to write?"

### Layer 4 — Hard-signal lint + typecheck (was: pattern library)

> **Revision 2026-04-25:** The original draft put a `.brewing/patterns/` directory here. Reviewer pushback (rightly): we already have many context docs (CLAUDE.md, context.md, code-map, manifest) and another loose-prose sibling adds navigation cost without payoff *until selective loading lands*. Meanwhile a hard-signal channel slowcook already scaffolds is unused: the `lint_command` and `typecheck_command` in `stack.json`. This layer is now lint-first; the patterns dir is reduced to its narrow original purpose (architectural prose lint can't capture) and only ships in concert with selective loading.

Brew's per-iteration feedback loop today reads vitest output only. `stack.json` has carried `lint_command: "npm run lint"` and `typecheck_command: "npm run typecheck"` since 0.7.0; nothing in `cli/brew/agent.ts` calls them. That leaves the cheapest, hardest signal channel unused.

**Wire-up:** after each iteration's edit, brew runs lint + typecheck alongside vitest. Errors enter the next-iter prompt as reds ("you broke `Type 'null' is not assignable to type '{ id: string }'` at `page.tsx:13`"). Hard signal — agent can't talk its way around an eslint rule or a TS error.

**Why this swallows much of the pattern-library scope:**

Most "low-level patterns" we'd want to capture are eslint rules waiting to be written:

- "Don't pass null to non-nullable props" → already caught by `tsc --noEmit` (TypeScript)
- "No synthetic `{ id: \"\" }` literals" → custom eslint rule
- "No relative imports in `src/`" → eslint config
- "Always `await cookies()` before `createClient(cookieStore)`" → custom eslint rule
- "No `console.log` in production paths" → eslint config

Custom eslint rules are higher fidelity than prose patterns because they fire on every edit, including the agent's. Issue #78 on rewo (the `viewer={null}` bug that drove this whole session) is **already** a type error — the agent shipped it because brew never ran typecheck during iterations.

**`.brewing/patterns/` reduced scope.** Reserve the directory for high-level architectural idioms that genuinely need prose ("how RLS works across our policies", "the lifecycle of a unification job"). Ship it with selective loading (Phase 2 below) so individual pattern files load only when the target test's tags or file paths match — otherwise the directory is just a fragmented context.md.

**Implementation cost:**

- Brew agent loop: ~30 lines to call lint + typecheck after edits, parse errors, fold into next-iter prompt
- Custom rule authoring: per-project; PM writes rules as bug classes are found (issue #78 → first custom rule, etc.)
- No new package; rule scaffolding lives in the consumer's eslint config, not slowcook

### Layer 5 — Semantic embeddings (RAG fallback)

Only when layers 1–4 return empty or the agent's last 3 read-without-write iterations indicate it can't find what it needs.

Triggers:

- Agent tool-use sequence shows ≥3 consecutive `grep` returning empty + `find_references` empty
- Agent's iteration_diff for 2+ rounds is zero-edits despite spending tokens (early signal of "I can't find the pattern I want to copy")
- Agent explicitly invokes `semantic_search(query)` tool

Backed by a file-based vector index (see next section). Returns top-k chunks with file path, line range, and relevance score. Agent decides which to read in full.

## Cross-brew provenance — shape

Story overlap is the norm, not the exception. An avatar-on-user-page story would re-traverse exactly the surface area story-005 / story-010 / story-011 mapped on rewo today. Without persistent memory, brew rediscovers wiring cold each time and frequently re-makes the earlier mistakes (e.g., the `viewer={null}` bug on story-005 was rediscovered as `getProfileByHandle` duplication on story-011).

The provenance index gives every new brew an iter-1 context block answering:

> "This surface area was previously touched by stories X, Y, Z. Their PRs were #A, #B, #C with these halt summaries: […]. Hot-spot files (touched in ≥2 brews): […]. Files with prior regressions: […]."

### Storage

`.brewing/provenance.json` — committed, JSON, evolves with the project. Incrementally maintained: each brew completion appends entity-level updates. Three index shapes:

```json
{
  "schema_version": 1,
  "by_file": {
    "src/app/(main)/u/[handle]/page.tsx": {
      "first_added_by": "story-005",
      "modified_by": ["story-005", "story-010", "story-011"],
      "last_brew": "story-011",
      "last_pr": "#94",
      "last_modified": "2026-04-25T22:24:00Z",
      "halt_count": 0,
      "regression_count": 1
    }
  },
  "by_symbol": {
    "MemberReactionsPage": {
      "file": "src/components/members/MemberReactionsPage.tsx",
      "kind": "component",
      "added_by": "story-005",
      "modified_by": ["story-005", "story-011"]
    },
    "getProfileByHandle": {
      "file": "src/lib/data/members.ts",
      "kind": "helper",
      "added_by": "story-N",
      "modified_by": ["story-N"]
    }
  },
  "by_route": {
    "/u/[handle]": {
      "stories": ["story-005", "story-010", "story-011"],
      "current_file": "src/app/(main)/u/[handle]/page.tsx"
    },
    "/api/members/[handle]/reactions": {
      "stories": ["story-005"],
      "current_file": "src/app/api/members/[handle]/reactions/route.ts"
    }
  }
}
```

### Maintenance

Two options, ship the cheaper one first:

- **Incremental append** (preferred): each successful brew run, `cli/brew/agent.ts` writes the entity-level diff into `.brewing/provenance.json` as part of the same commit that lands the impl. Cheap, eventually consistent, single-source-of-truth.
- **Derive on demand**: `slowcook provenance regenerate` walks git history + iter logs + PR bodies. Slower; useful as a one-time bootstrap when slowcook lands on a project that already has brew history. Implementation deferred until needed.

### Loaded by brew at iter 1

When the new brew's manifest is computed, also derive the entity set the story is likely to touch (from spec proposals: routes, schema, components mentioned in invariants). Cross-reference against `.brewing/provenance.json` and inject the relevant entries into the iter-1 prompt as a "prior context" block. Limited to entries the new brew actually overlaps with, not the whole index.

### Why this is Phase 1, not Phase 2

The mandatory discovery step (Phase 1) asks "is there an existing entity that does what I'm about to write?" Provenance answers a strictly bigger question: "what's the history of this surface, including failed attempts and regressions?" Both feed into the same iter-1 context block. Splitting them puts the agent in Phase 1 with half the context — it re-rediscovers things Phase 2 would have surfaced. Bundle them.

## File-based vector store — shape

User instinct (2026-04-25): the vector store should be **local and file-based**, ideally committed to the repo, so reproducibility and CI both work without external services. That's right with one nuance:

**Commit the manifest, optionally commit the blob.** The manifest is small JSON tracking which files were embedded, their content hashes, chunk metadata. The blob is the actual vector data and can be ~10–50 MB on a brownfield project. Git history of the blob bloats badly; the manifest doesn't.

### Layout

```
.brewing/embeddings/
  manifest.json                # always committed
  index.db                     # sqlite-vec; commit OR gitignore based on size policy
```

`manifest.json` shape:

```json
{
  "schema_version": 1,
  "embedding_model": "voyage-code-3",
  "embedded_at": "2026-04-25T00:00:00Z",
  "chunks": [
    {
      "file": "src/lib/supabase/server.ts",
      "lines": [1, 42],
      "hash": "sha256:...",
      "chunk_id": "c001"
    }
  ],
  "total_chunks": 1842,
  "blob_committed": false
}
```

`blob_committed: false` means the consumer chose to gitignore `index.db` and rebuild it on first checkout. `blob_committed: true` means the .db file ships with the repo. Slowcook's loader checks the manifest, finds missing/stale chunks, regenerates only those.

### Commit-the-blob policy

A `.brewing/embeddings/policy.json`:

```json
{
  "commit_blob_when_total_chunks_under": 5000,
  "embedding_model": "voyage-code-3",
  "chunk_size_lines": 60,
  "chunk_overlap_lines": 10
}
```

Default: blob committed when project has fewer than ~5K chunks (≈2K source files). Above that, gitignored and rebuilt locally. Threshold configurable.

### Format choice — sqlite-vec

Single file, universal tooling (sqlite is everywhere), no external service, queryable from Node directly via `better-sqlite3` + `sqlite-vec` extension. Reasonable cold-start (load db file, run vector search in-process).

Alternatives considered:

- **Plain JSON of vectors**: shippable but slow at query time; OK for <500 chunks
- **lance**: columnar, fast, newer; more infra than needed
- **annoy / hnswlib**: C/Python centric, harder Node integration
- **External (Pinecone / Qdrant)**: violates the "local + file-based" goal

Going with sqlite-vec. Drop-in if a future project genuinely needs multi-tenant scale; today's projects don't.

### Embedding model

Default: `voyage-code-3` (good code embeddings, reasonable cost). Configurable via `policy.json`.

Costs (rough, 2026 prices):

- Initial embedding pass on a 5K-chunk project: ~$2–5
- Re-embed on commit batch: pennies (only changed files re-embed)
- Index file size: 5K chunks × ~4KB int8-quantized vectors ≈ 20 MB

For a closed-source brownfield: not catastrophic. For an OSS project that runs slowcook as a one-off: acceptable.

## Phasing — three releases, each independently shippable

### 0.11.x — Lint + typecheck signals (Phase 0 — ships first)

Smallest useful slice in the whole plan; doesn't even need brownfield to justify it. Closes the bug class that gave us issue #78 (`viewer={null}` to a non-nullable prop) and rewo's whole story-010 → story-011 detour. Should ship before any retrieval-layer work.

**Ships:**

- Brew's per-iter loop calls `stack_config.test.lint.lint_command` and `lint.typecheck_command` after each successful edit.
- Lint/type errors fold into the next-iter prompt as additional reds with file:line locations. Same shape as vitest failure messages today.
- New halt class `LINT_ERRORS_PERSIST` after N iterations of unfixed lint reds (prevents thrashing).
- No-op when `stack.json` doesn't define `lint_command` / `typecheck_command`. Optional, not required.

**DoD:** synthetic regression test — re-running rewo's broken story-005 brew (`viewer={null}` synth) hits a typecheck error in the first iter and brew can't ship the wiring.

### 0.11.x+1 — Symbol-aware retrieval + mandatory discovery + cross-brew provenance (Phase 1)

Three coordinated parts shipped together. They all answer variants of the same question — "what's already here?" — and splitting them would give the agent half the context.

Closes the **silent-duplication** failure mode (rewo PR #94 demonstrated it: `getProfileByHandle` duplicated between page.tsx and existing API route) AND the **cold-rediscovery** failure mode where each new brew on overlapping surface re-traverses the same wiring without learning from prior brews' halts and regressions.

**Ships:**

- **Symbol-aware tools** exposed to the agent: `find_references(symbol)`, `find_implementations(interface)`, `find_definition(symbol)`. Implementation in `@slowcook-ai/cli` (or new `@slowcook-ai/retrieve`) using ts-morph (already in dep tree).
- **Cross-brew provenance index** at `.brewing/provenance.json` (see "Cross-brew provenance — shape" above). Maintained incrementally: each successful brew appends entity-level updates as part of its impl commit. Per-iter loader picks entries overlapping the current story and injects them as a "prior context" block in iter-1.
- **Mandatory pre-write discovery requirement** in brew's iteration prompt:
  > "Before writing any new exported symbol (function / component / type / route), search for existing similar entities. Use `find_references` for symbol-named candidates and `grep` for concept-named candidates. Consult the prior-context block: if a previous brew touched this surface area, read its PR body for context before duplicating its logic. If you find a candidate that fits the new requirement (possibly with a small extension), EXTEND IT instead of creating a parallel symbol. If you decline to extend, state the reason in your turn output."
- **Iteration log gains a `discovery:` field** capturing what was searched + what was found (including provenance hits) + what the agent decided. Visible in the run log and the brew PR body so the reviewer sees the reasoning trail.
- Tool calls counted against budget like file reads.

**Why all three halves together:**

- **Tools alone:** agent has the capability but no incentive to use it. Cheapest local move is "write new code." Soft prompt instructions don't stick — proven on the supersede field round 2/3 today.
- **Requirement alone:** agent has nothing to call. Agent fails discovery, brew halts.
- **Tools + requirement, no provenance:** agent finds same-brew entities but is blind to prior-brew context. Repeats earlier mistakes (re-implementing patterns prior brews already established, missing regression risks).
- **Provenance alone:** agent sees history but can't query the live codebase for current state.
- **All three + iteration-log accountability:** agent demonstrably looked at both current code AND brew history before writing, with a reasoning trail visible to the reviewer.

**DoD:**
1. Brew on a 1K–5K-file synthetic brownfield project completes a CRUD story where the right answer is "add an arg to existing function" — without creating a parallel function. Iteration log's `discovery:` field shows it found the existing function and extended it.
2. A second brew on overlapping surface (e.g., story extending a page another story brewed) shows the prior-context block in iter-1 referencing the prior brew's PR and avoids re-implementing entities that brew added.

### 0.11.x+2 — Code-map signatures + lazy loading + pattern library (Phase 2)

Three coordinated additions:

**A. Function-signature enrichment in code-map.**

Each exported symbol gains its signature + caller count + file:line:

```json
{
  "kind": "helper",
  "file": "src/lib/data/members.ts",
  "exports": [
    { "name": "getProfileByHandle",
      "signature": "(handle: string) => Promise<Profile | null>",
      "callers": 3, "line": 42 }
  ]
}
```

Computed by ts-morph on `slowcook map generate`. Cheap (single AST pass, runs already). Emits to existing `.brewing/code-map.json`. Phase 1's `find_references` tool consumes the same data.

**B. Lazy code-map computation.**

`slowcook code-map --derive-for <test-id>` returns a subset starting from the target test → imports → their imports (depth-bounded). Injected per-iter instead of the full map. Closes the "code-map exceeds prompt budget on 5K+ file projects" pain.

**C. Pattern library with selective loading.**

`.brewing/patterns/` scaffolding via `slowcook bootstrap` (companion to §0.11.0). Auto-extracted draft patterns; PM curates. **Reserved for prose-only patterns** — anything expressible as a lint rule belongs in eslint config (Phase 0), not here. Each file tagged so the loader can pick relevant patterns per target test, not the whole directory.

**DoD:** brew on a 5K-file project loads only the pattern files + code-map slice relevant to the target test. Discovery step (Phase 1) sees signatures in the code-map and finds candidates without separate `find_references` calls when the answer is already in the lazy slice.

### 0.11.x+3 — Embedding fallback (Phase 3)

Only for projects where Phases 1–2 leave gaps.

**Ships:**

- `slowcook embeddings build` command: scans source, chunks, embeds, writes `.brewing/embeddings/index.db` + `manifest.json`.
- `slowcook embeddings refresh` for changed files only.
- New agent tool `semantic_search(query, k=5)` returning top chunks.
- Trigger logic that auto-fires Phase 3 when Phase 1/2 return empty + agent is searching.
- Default-off; consumer enables via `.brewing/stack.json: { "retrieval": { "embedding_fallback": true } }`.

**DoD:** brew on a 50K-file synthetic monorepo retrieves the right helper file via `semantic_search` when symbol-aware search returns empty (because the variable naming doesn't match).

## What this is NOT

- **Not RAG-first.** Embedding search is the last fallback, not the entry point. Most agent retrieval should be answered by layers 1–4.
- **Not a replacement for `context.md`.** Pattern library + DISCOVERY.md complement context.md; they don't replace it. context.md stays the single hand-authored anchor.
- **Not a vector DB service.** sqlite-vec single-file index. No Pinecone, no Qdrant, no Supabase pgvector dependency for the retrieval layer (Supabase pgvector remains an option for the consumer's app, not slowcook's retrieval store).
- **Not auto-RAG-on-by-default.** Embedding fallback is opt-in via stack.json. Small projects never see the embedding cost.

## Evidence to gather before locking Phase 3

Before committing to RAG, instrument brew (some of this lands earlier):

- Per-iter: count of tool calls before first write, file-read frequency, repeat-read patterns
- Per-halt: did the agent's last rationale say "I couldn't find an example of X"?
- Per-success: which retrieval layer was the marginal contributor?

If Phase 1 + 2 close ≥90% of brownfield halts measured against a benchmark project, Phase 3 stays opt-in indefinitely. If the residual 10% is structurally unreachable without semantic search, Phase 3 ships per the design above.

## Open questions

- **Cross-file conceptual queries** (e.g., "tenant scoping") are harder than single-symbol lookups. ts-morph helps with literal symbol references; semantic clustering of "tenant-related code" probably needs embeddings even with a great pattern library. May need to revisit the Phase 2/3 boundary once we have data.
- **Embedding model versioning.** Upgrading models invalidates the index (vectors don't compare across models). Plan: version is in `policy.json`; mismatch on load triggers full rebuild. Handles model upgrades; doesn't handle downstream API price/availability changes gracefully.
- **Patterns extracted at bootstrap may be stale within 6 months.** Should `slowcook bootstrap --refresh` re-extract patterns? Probably yes, but conflict-resolution with PM-edited patterns is its own problem. Defer to actual brownfield use.
- **Multi-language.** The whole plan assumes ts-morph as the symbol-aware layer. Polyglot brownfields (TS frontend + Python backend) need per-language retrieval modules. Out of scope here; revisit when slowcook adds a non-TS stack adapter.
