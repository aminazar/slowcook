# 0.14 — Mockup-first refinement

> Status: drafted 2026-04-24. Vision / architectural sketch. Implementation waits on 0.11.0 (textual proposals) + 0.10.1 (vision-capable `LlmClient`). Both shipped.
>
> **2026-04-25 reorder (final):** previously slotted as 0.12 then 0.13. Now **0.14** — the bug-flow + chef + testgen→recipe rename track in [`0.13-bug-flow-and-chef.md`](./0.13-bug-flow-and-chef.md) is shipping as 0.13.0 (alphas in flight at time of writing). Mockup-first is the next major after that lands. No technical dependency between this plan and bug-flow or brownfield retrieval; ordering is purely priority.

## Why

Textual refinement (0.11.0) proposes schemas, tokens, routes as YAML + Mermaid. That's a large improvement for *technical* proposals — but for UI, text is the wrong medium. PMs negotiate UI by looking at the UI.

Operator experience with Claude Code shows the alternative: "prompt an agent to build a React mockup, iterate via feedback on the live prototype, keep the resulting code as the foundation of the real app." No abstraction gap between design review and production; mockup code is the first commit of shippable code; feedback velocity is near-conversational.

This doc codifies that pattern as a slowcook refinement mode.

## Core architectural commitment

**The mockup lives at its production location — not in a sidecar directory.** Mock data is swapped in via a data-layer seam:

```
src/app/(main)/notifications/page.tsx           # real location
src/components/notifications/NotificationList.tsx
src/lib/data/notifications.ts                   # real fetches (brew writes this)
src/lib/data/notifications.mock.ts              # hardcoded fixtures (refine writes this)
```

The page/component imports from `@/lib/data/notifications`. At build or runtime, an env flag (`MOCK_STORY_042=1`) picks the mock implementation via Next's conditional resolution (or a thin factory). When brew takes over, it writes the real implementation + deletes the env flag. The component, tokens, validation, event handlers — untouched.

This converts "mockup" from disposable to **foundational**. PM's approved visual + behavior lands in production verbatim.

## Phase-by-phase flow

```
issue → refine(spec + mockup) → PM-iterate → freeze → testgen → brew(wire-up) → ship
```

### 1. Refine generates mockup

Refine agent's output grows from {spec YAML, proposals block} to:

- `specs/story-N.yaml` with `proposals:` (unchanged from 0.11.0)
- `src/**/` route + components for the story's pages (new)
- `src/lib/data/<domain>.mock.ts` with hand-authored fixtures (new)
- `src/lib/data/<domain>.ts` with `@slowcook-stub` body that throws (new — brew replaces)
- `.env.development.story-N` setting `MOCK_STORY_N=1` (new)

Agent prompt additions:

- "Use project design tokens from `.brewing/context.md` Visual Conventions section"
- "Reuse existing components in `src/components/` when applicable — reference by import path"
- "Data layer calls route through `src/lib/data/<domain>` for swappability"
- "Event handlers + validation + loading / disabled states must all work against mock data — PM will test by clicking"

### 2. Preview deployment

Consumer provides a preview-URL template in `.brewing/context.md`:

```
preview_url_template: "https://{repo}-git-{branch-slug}.pages.dev"
```

Refine generates that URL from the branch name and puts it in the PR body. Actual preview deployment is the consumer's CI (Cloudflare Pages, Netlify, Vercel — already a solved problem outside slowcook).

Graceful degradation: if no preview URL template is configured, PR body says "review locally: `git fetch origin <branch> && npm run dev`".

### 3. PM iterates

PM opens preview, clicks through, finds issues. Two feedback shapes, same trigger:

**Prose** — "the unread badge should be coral, not green"
**Annotated screenshot** — PM marks up a screenshot with arrows / circles / text, attaches to PR comment

Both triggered by `/refine` command on the comment. Workflow:

1. Refine reads all unresolved PR comments since last refine commit
2. If any comment has image attachments, Claude vision receives (original screenshot from mockup | annotated image | prose) triple → summarises what changed
3. Agent produces a diff against current branch state
4. Force-pushes (preserving branch; amending spec + mockup files)
5. Posts summary comment: "Updated per @pm's feedback: changed unread-badge color to coral; re-rendered. New preview deploying."
6. Cloudflare rebuilds preview (~60s)
7. PM re-reviews. Approves OR iterates again.

### 4. Freeze

PM approves the spec PR. Merge fires testgen:

- Tier-1 UI tests recorded against MOCKUP behavior (validation rules, disabled states, loading spinners) — mockup IS the spec in executable form
- Tier-1 handler tests generated from spec YAML's API contracts
- Schema assertion from proposals block's approved DDL
- Styling presence test with consumer's tokens

The mockup's tier-1 test coverage is FULL by construction — every interaction the PM approved becomes an assertion.

### 5. Brew wires up

Brew's allowed-paths on this story explicitly include:
- `src/lib/data/<domain>.ts` (replace stub with real fetch)
- `supabase/migrations/*.sql` (from approved schema proposal)
- API route handlers

Brew's target tests: the new tier-1 UI tests (which pass against mock data TODAY; brew's job is to keep them passing when `MOCK_STORY_N=0` is the default). Also the schema + handler tier-1 tests.

Brew does NOT need to touch the mockup files — they're already correct.

### 6. Ship

`.env.development.story-N` file is deleted in the brew PR. The mockup fixtures file stays (now named `<domain>.fixtures.ts` or kept as `@slowcook-stub` marker?) — it's reference data for tests, not production.

## Cost model

Token cost per refine cycle with mockup generation: **~$2-5** (vs ~$0.30 for spec-only today). Iteration loops can hit **$10-20** across 3-5 rounds for a non-trivial story.

Mitigations:

- Per-story budget cap in consumer config (default $20, warn at $15)
- `/refine --no-mockup` opt-out for stories where PM is happy with textual proposals
- Incremental mockup updates: agent only rewrites touched components, not the full set — cheaper per iteration

## Tradeoffs called out

1. **Drift risk.** PM approves mockup behavior → brew wires backend → backend validation differs. Mitigated by tier-1 UI tests being recorded against mockup; brew can't ship without them still passing. Approved mockup IS the UI spec.

2. **Preview infra dependency.** Without a preview URL, PM reviews locally. Works but slower. Consumer ops task, not slowcook's to solve.

3. **Code-in-refine prompt surface.** Refine now generates 500+ lines of React; prompt-eval surface grows significantly. Probably ships with a slowcook-opinionated starter template (use Tailwind, use server components for data-fetching in refined form, use a specific state-management pattern) — consumers customise via context.md.

4. **Reviewability.** Code-diff on a 500-line mockup is ugly in GitHub. PR body should render screenshots + preview link PROMINENTLY; the code is secondary. Could auto-generate a PR body section: "Mockup behavior summary: [bullets of event handlers + state transitions derived from the generated code]."

5. **LLM capability.** Requires the LLM to produce idiomatic React + Tailwind at scale, against a specific consumer's design system. Claude Opus + Sonnet both strong here (Claude Code's track record). Concrete — not speculative.

## Prerequisites

- **0.11.0 — textual proposals.** Mockup is an extension of the proposals framework.
- **0.10.1 — vision-capable `LlmClient`.** For reading annotated screenshots.
- **0.10.2 — Gate 3 HITL PR-comment pattern.** Provides the shape for annotated-screenshot replies.
- **Recorder fixture format (0.9.1).** Mock data is a recorder fixture conceptually; symmetric interface.
- **Preview deployment convention.** Consumer responsibility. Slowcook documents the URL-template pattern in context.md.

All prerequisites are on the roadmap or shipped. 0.12 is the coherent next major step after 0.11 + 0.10.1 + 0.10.2 land.

## Out of scope

- **Figma import / export.** Slowcook doesn't own design tooling; Figma stays for high-fidelity pixel specs if the consumer uses one. Mockup-first refinement is explicitly the "we don't need Figma for most stories" answer.
- **Cross-device mockup testing.** Preview URL is browser-accessible; PM tests on their own device matrix. Slowcook's Gate 1 + screenshot-matrix (0.9.2) cover the CI-time multi-viewport checks.
- **Generated mockups without consumer design tokens.** If `.brewing/context.md` Visual Conventions is empty, refine falls back to Tailwind defaults — not useful. Prerequisite: context.md is populated (brownfield bootstrap in 0.11+ handles this).

## Open questions

- **State management pattern.** Mockup needs client-side state to feel interactive. Do we opinionate (React Context, Zustand, ...) or detect from the consumer's existing code? Detection is cleaner but harder.
- **Handling "the PM wants to start fresh."** Some iterations result in PM saying "throw it out; try a list layout instead of cards." Does refine blank the slate, or diff? Probably diff by default; `/refine --regenerate` for restart.
- **Mockup fixture lifecycle.** When brew wires up the real data layer, do the fixtures stay (for tests) or go (replaced by recorder captures)? Probably stay — they're orthogonal to recorded fixtures (mockup fixtures describe intent; recorded fixtures describe reality).

## Target timeline

Not a 2026-Q2 target. Depends on 0.11.0 shipping cleanly first + 0.10.1 vision-capable LlmClient + sufficient Claude-Code-like track record on generating idiomatic consumer-specific React. Plausible 2026-Q3 slice if the prior releases land on schedule.

Ship textual proposals (0.11.0) first. Prove out the proposal-plus-iterate machinery. Then tackle the bigger leap.

## UI vs diagrams — two different review surfaces

Mockups solve the UI negotiation; they don't replace technical diagrams. Keep both lanes, use each for what it's best at:

| Artifact | Medium | Review method |
|---|---|---|
| Schemas / data model | **Mermaid `erDiagram`** | Text review by entity name (GitHub renders inline) |
| Sequence / flows / state machines | **Mermaid `sequenceDiagram` / `flowchart` / `stateDiagram`** | Text review by named step |
| Architecture diagrams | **Mermaid `flowchart`** | Text review by named component |
| UI mockups | **React + Tailwind + mock data** | Live preview review via element-anchored comments (see §Review UX) |
| Screenshot of a specific defect | PNG + annotated reply | Claude vision + positional reading |

Don't try to mock up a database ERD in React. Don't try to render a schema in pixels. The right tool for each:

- Mermaid is **diff-able text**; the agent can amend it in response to prose feedback (`"make the FK on notifications.actor_id nullable"`).
- React mockup is **running code**; the PM tests it as they'd test the app, comments on actual elements.

Refine emits both: Mermaid for every diagram category, React for every UI page the story introduces. Both committed to the refine PR; both reviewable in one thread.

## Review UX — modal toggle, not gestures

PM testing a mockup needs to BOTH interact with it (click a button to open a dropdown) AND leave comments on specific elements. Those two goals can't share the same gesture without ambiguity.

**Commitment: modal pattern with a persistent floating toggle.** Detail lives in the companion doc `0.12.1-review-overlay.md`. Key points:

- Test mode is the default. All interactions behave normally. Toggle visible in the top-right (desktop) / bottom-right (mobile).
- Press the toggle → enters review mode. Background gets a subtle tint; cursor becomes a crosshair. Click captures `{element-selector, screenshot, coords}` and opens a comment input.
- Exit via the toggle, `Escape`, or re-press on mobile.
- Keyboard shortcuts (`R` to toggle, `C` on hover to quick-comment) are power-user bonuses — discoverable via help, never the primary path.
- No ctrl/cmd+click, no long-press, no two-finger tap — all conflict with either the browser or the OS.

**Why modal beats gestures**: no conflicts, discoverable, same UX cross-platform, unambiguous state, mistake-proof. Detail + mobile specifics in 0.12.1.

## Brownfield extraction — the symmetric path

Everything in this doc assumes **greenfield** (refine generates artifacts from thin air). For **brownfield** consumers — slowcook adopted into an existing repo that already has schemas, components, designs — refine needs the same artifact shapes, but **extracted** from extant code, not generated.

Principle: the artifact SHAPES converge. The same files refine writes on greenfield, `slowcook map` (or a new `slowcook bootstrap`) extracts on brownfield. Refine reads the SAME file layout in both cases and proposes future work **aligned to existing conventions**.

Extraction targets (extending `slowcook map` — already the "what's in this repo" lens):

| Artifact | Greenfield: refine generates | Brownfield: map/bootstrap extracts |
|---|---|---|
| `.brewing/diagrams/schema.mmd` | From story's schema proposal | Parse `supabase/migrations/*.sql` → Mermaid `erDiagram` |
| `.brewing/diagrams/flows.mmd` | From API + component flow descriptions | Trace handler call-chains + Supabase client usage → sequence diagrams |
| `.brewing/diagrams/components.md` | Proposed components + props shape | ts-morph walk of `src/components/**` → catalog: export name, props type, role classification (primary button / form input / card / list row / etc.), screenshot link |
| `.brewing/diagrams/design-tokens.md` | From story's ui_layout proposal | Parse `globals.css` CSS custom properties → Tailwind utility names + sample color swatches |
| `.brewing/diagrams/routes.md` | From story's routes proposal | Walk `src/app/**/page.tsx` → path-to-file mapping + auth state from middleware |

Refine reads all of these on every run. When processing a new issue:

- Brownfield: "this repo uses `coral` for CTAs and `mint` for success; reuse those" — extracted from the tokens catalog
- Brownfield: "the repo has a `<Card>` primitive at `src/components/ui/Card.tsx`; use it for this new feature instead of proposing a new container component" — extracted from the components catalog
- Brownfield: "the `notifications` flow should follow the existing `reactions` sequence shape: handler → `rewo_reactions` insert → trigger → realtime broadcast" — extracted from flows
- Brownfield: "the schema has `profiles`, `rewos`, `rewo_reactions`, `connections`, `invites`, … — extend as needed; name new tables consistent with singular/plural conventions already in use"

Result: refine's proposals on brownfield are **immediately aligned** with the repo's conventions. No "wait, the agent invented a button style that doesn't match" surprise.

This elevates `slowcook map` from "brew-time code-awareness" (today's role) to "refine-time project-awareness" (0.12+ role). Same tool; expanded surface.

### Implementation shape for brownfield extraction

- `slowcook map` gains `--emit-diagrams` / `--emit-catalog` flags (default OFF to preserve today's behavior)
- Or a new sibling: `slowcook bootstrap` that runs `map --emit-*` + writes context.md stubs + commits everything as the repo's slowcook-awareness baseline
- Runs once per repo (on adoption); re-runs periodically (or in CI) to keep catalogs fresh
- Artifacts in `.brewing/diagrams/` are frozen from brew's allowed-paths (same treatment as `.brewing/manifests/`); map updates them, brew reads them, nothing else writes

Scope reference: this is the "brownfield cooker" from the original roadmap (`docs/plans/roadmap-0.7-to-0.11.md`) but narrowed to the extraction-for-refine case. The wider brownfield work (auto-generating test fixtures from existing behavior) is distinct and later.
