# 0.7 plan — testgen two-tier redesign

> **Status:** draft, 2026-04-21. Motivated by two failed brew runs against rewo on 2026-04-21 (story-001 + story-003) where every iteration reverted for no-progress. Root cause is not in brewing — it's in testgen's output layer. Brewing did its job and correctly diagnosed the mismatch in the halt reports.

## 1. Summary

Today's testgen emits a single tier of tests: HTTP-loopback integration tests that `fetch(BASE_URL + '/api/...')`. These tests are **unratcheable** without a live server + real external services, so brewing burns budget without being able to produce a green-gain. This plan splits testgen's output into two explicit tiers:

- **Tier-1 (integration)** — fast, in-process, mocks external services at the module boundary. This is what brewing's ratchet runs on every iteration.
- **Tier-2 (acceptance)** — Playwright / full-stack HTTP, runs against a real sandbox (local `supabase start` or staging). Gated by `ACCEPTANCE=1`. Runs nightly + pre-merge, not during brewing.

The chicken-and-egg of tier-1 (tests can't collect until the impl module exists) is solved by having testgen write minimal throwing stubs in `src/` alongside the tests (**Option A**). Brewing replaces the stubs; human reviewers know from the testgen PR body that `src/` files included were stubs.

## 2. Evidence: why now

Two brew runs against rewo (cli@0.6.3, claude-opus-4-7, $10 each):

| Story | Test shape | Iterations | Checkpoints | Outcome |
|---|---|---|---|---|
| 001 | Rendering (React component, needs DOM + next/navigation mocks) | 4 | 0 | crashed on iter-5 API 400 (credit) — zero code-edit progress in 4 iters |
| 003 | HTTP-loopback (`fetch(localhost:3000)` — no server running) | 6 | 0 | BUDGET_EXHAUSTED — iters 4-6 produced `files_changed: 0` (agent gave up) |

Slowcook's `generateDiagnosis` correctly auto-labelled the halt: *"target test is likely unreachable from the code the agent is editing — a layer mismatch."* The diagnosis is right. The fix is in testgen.

Cost evidence: roughly $12 of real money burned per dead-end story. At current test shape, no amount of brewing-side tuning can recover that — the signal never reaches the agent.

## 3. Goals / non-goals

**In scope:**
- Testgen emits tier-1 integration tests that brewing can actually ratchet against.
- Testgen emits matching minimal stubs in `src/` so tier-1 tests collect.
- Testgen reads `.brewing/context.md` so it conforms to project-specific mock conventions (already spec'd in `project_pause_state.md#1b`; ship as part of this work).
- Refine agent's prompt updated to steer specs toward handler-call-level invariants (testable from mocks), away from semantic-outcome language (only testable against real services).
- Existing testgen output for rewo stories 001/003/004 migrated (moved to `tests/acceptance/`) so they aren't lost but aren't in brewing's path either.

**Out of scope (separate tracks):**
- Tier-2 (acceptance) discovery + runner integration. Playwright support is its own line item, probably slowcook 0.9-ish, and this plan just reserves `tests/acceptance/` as the location.
- Multi-stack: this plan is TypeScript/vitest-specific. Python/Go/Java adapters are separate.
- Deleting the existing HTTP-loopback tests — keep them under `tests/acceptance/` for now; decide later whether to port or drop.

## 4. Target shape

### 4.1 Tier-1 (integration) — the ratchet layer

Location: `tests/integration/story-N.test.ts`. One file per story.

Shape:

```ts
import { describe, it, expect, beforeEach } from "vitest";
import { POST } from "@/app/api/rewos/route";
import { mockSupabase, resetMocks } from "@/tests/helpers/mocks";

describe("POST /api/rewos — ungated for authenticated members (story-003)", () => {
  beforeEach(() => resetMocks());

  it("returns 201 for an unverified member with a valid payload", async () => {
    const supabase = mockSupabase({
      auth: { user: { id: "u1", verified: false } },
      insert: { table: "rewos", returning: { id: "rewo1" } },
    });

    const req = new Request("http://test/api/rewos", {
      method: "POST",
      headers: { Authorization: "Bearer unverified", "Content-Type": "application/json" },
      body: JSON.stringify({ title: "hi", body: "hello" }),
    });
    const res = await POST(req);

    expect(res.status).toBe(201);
    expect(supabase.from).toHaveBeenCalledWith("rewos");
  });
});
```

Note: `mockSupabase` is a thin helper that today wraps hand-authored response shapes via `vi.mock`. When the tier-2 recorder lands (§9.4), the *same* helper signature switches to fixture-backed replay without touching this test. See §4.3 for the contract.

Properties:
- Imports the route handler directly — no HTTP server.
- Mocks external dependencies (`supabase`, `resend`, `stripe`, etc.) at the **module boundary** using `vi.mock`.
- Builds a `Request` object in-process, calls the handler, asserts on the `Response`.
- Runs in <1 s per test. Deterministic. Safe to run 50+ times in a brew loop.
- Fails at runtime with "not implemented" until brewing fills in the route — which is exactly what the ratchet needs.

### 4.2 Tier-2 (acceptance) — the reality layer

Location: `tests/acceptance/story-N.spec.ts` (Playwright) or `tests/acceptance/story-N.test.ts` (backend-only).

Properties:
- Runs against a real sandbox: `supabase start` locally, or a staging project in CI.
- Full HTTP stack with `next dev` running. Real external services (or their sandbox endpoints).
- Gated by `ACCEPTANCE=1`. Not in vitest's default include.
- Runs nightly (cron workflow) + pre-merge (PR check). Never in brewing's loop.
- Catches drift between tier-1 mocks and real external behaviour within 24 h.

### 4.3 Record-and-replay — how the two tiers share a contract

**The hand-authored-mock problem.** Every tier-1 mock is a guess about what the real service returns. A test with wrong mock shape passes locally and fails in production. Tier-2 nightly is the canary, but the gap between "tier-1 went green" and "tier-2 says the mock lied" can be hours to days.

**The pattern.** Tier-2 tests run against real services with a recorder wrapped around each external client. Every `request → response` pair is scrubbed and written to `tests/fixtures/<story-id>/<service>/<request-hash>.json`. Tier-1 tests mock the same boundary but, instead of hand-typed shapes, replay the recorded fixture. Re-running tier-2 periodically refreshes the fixtures. Any drift shows up as a `git diff` under `tests/fixtures/` — immediate, reviewable, bisectable.

**Why this is better than hand-authored mocks:**
1. Mock shapes are always correct — they literally came from the service.
2. Drift detection is automatic: re-record, diff fixtures, investigate changes.
3. Test authoring is faster: write the intent, let the first tier-2 run populate fixtures.
4. Reviewers audit what the service actually did, not what we thought it would do.

**Tradeoffs and risks:**
- **Fixture staleness.** If tier-2 isn't run, fixtures silently become fiction. Mitigation: CI enforces a max age (e.g., fail builds if the newest fixture is >14 days old and no `@fixtures-frozen` marker is present).
- **Determinism / scrubbing.** Recorded responses contain timestamps, UUIDs, session tokens, real user emails. A scrubber pass MUST run before writing to disk — replace volatile fields with stable placeholders per a config that lives next to the fixtures. Loud default: scrub everything unless allow-listed.
- **Security.** Scrubber bugs leak production PII into git history. Mitigation: scrubber has its own test suite; CI fails if any fixture contains a pattern matching an email/UUID/bearer token that wasn't placeholder'd.
- **Storage.** JSON fixtures are human-readable but bulky. Acceptable until a single story's fixtures pass ~1 MB, then revisit (compress, or store out of repo).
- **Second chicken-and-egg.** Tier-1 needs fixtures to replay; first tier-2 run produces them. Before the first run, tier-1 either skips ("no fixture, no test") or falls back to hand-authored minimal mocks. Must not block the brewing ratchet during early-story development.
- **Recording isn't free.** A tier-2 run that records costs more than one that just asserts. Acceptable — tier-2 runs nightly, not per-iteration.

**Scope for this plan:**
- **Out of scope** to implement: recorder, fixture format, scrubber config, replay helper. All of that is tier-2 runner work (§9.4, probably 0.9).
- **In scope to reserve**:
  - Fixture path convention: `tests/fixtures/<story-id>/<service>/<hash>.json`.
  - Tier-1 output uses thin *helper functions* (e.g. `mockSupabase(fixtureKey)`) rather than deeply nested inline `vi.mock({ from: vi.fn()...})`. The helper today wraps hand-authored shapes; when the recorder lands, the same helper switches to fixture-backed. Every tier-1 test stays unchanged through the migration.
  - Testgen's prompt MUST emit tests that call those helpers, not inline mocks, so we don't paint ourselves into a corner.

**Why raise this now, when the recorder ships later:** if 0.7 emits 200-line tests with deeply-nested inline `vi.mock` blocks, swapping to fixtures in 0.9 means regenerating every test. A helper abstraction now keeps that future swap a single-helper-file change instead of a fleet-wide rewrite. This is pure optionality cost.

### 4.4 Why not just make brewing run `next dev` + `supabase start`?

- 30-90 s startup per brew iteration × 10-50 iterations = unworkable.
- Docker-in-Docker on self-hosted runner is fragile.
- Supabase schema drift between brew runs is hard to reset cleanly.
- Even when it works, tier-1 is still the right layer for "did the handler call the right mock?" — tier-2 adds semantic confidence but with O(minutes) feedback.

## 5. Chicken-and-egg: testgen writes stubs (Option A)

**Problem.** Tier-1 tests `import { POST } from "@/app/api/rewos/route"`. At test collection time, vitest must be able to resolve that import. If the route file doesn't exist, collection fails before any test runs — brewing has nothing to ratchet against.

**Option A (chosen).** Testgen, when writing `tests/integration/story-N.test.ts`, ALSO writes a minimal stub in `src/app/api/.../route.ts`:

```ts
// THIS FILE IS A STUB generated by slowcook testgen for story-003.
// Brewing will replace this body. Do not merge this file unmodified.
export async function POST(req: Request): Promise<Response> {
  void req;
  throw new Error("not implemented (story-003 stub)");
}
```

Properties:
- Exports the right symbols with correct types.
- Tests collect cleanly, fail at runtime with a clear message.
- Brewing replaces with real impl (same file, same symbols) — no file-creation machinery needed in brewing.
- The testgen PR body lists every stub file so reviewers can't miss them.
- A `// @slowcook-stub story-003` marker in each file makes mechanical detection easy for future tooling.

**Options rejected:**
- **Option B** (brewing creates stubs as iteration 0): cleaner separation but needs a new brewing phase + complicates budget accounting.
- **Option C** (type-only `.d.ts` stubs): vitest's ESM resolution doesn't treat `.d.ts` as a module at runtime; import would still fail at test execution.

## 6. Refine-agent changes

Specs need to be expressible as tier-1 assertions. That means invariants should talk about **what the handler does** (observable at the module boundary), not **what the service does** (only observable against reality).

Add to `REFINEMENT_ANALYST_SYSTEM` (packages/cli/src/commands/refine/prompts.ts):

> When writing invariants for endpoints that call external services (Supabase, email, payments), prefer statements at the **handler-call level** over statements at the **semantic-outcome level**:
>
> - ✅ "Handler calls `supabase.auth.signInWithPassword` with the provided credentials"
> - ✅ "On a successful DB insert, handler returns 201 with the persisted row"
> - ❌ "The user is authenticated against Supabase"
> - ❌ "A row exists in the database after the request"
>
> The first form is testable in tier-1 integration tests (which mock the boundary); the second requires tier-2 acceptance tests against a real sandbox.

This is additive guidance, not a hard rule — some invariants genuinely need tier-2. The goal is to not write tier-2-only invariants by accident when a tier-1 form exists.

## 7. Testgen scope changes

### 7.1 Inputs testgen reads

Currently: `specs/story-N.yaml`, optional `.brewing/stack.json`.

After: add `.brewing/context.md` (the consumer-project brewing context file). `buildProjectContext` already exists in `packages/cli/src/commands/testgen/agent.ts` — needs a one-line edit to prepend `readContextMd(repoRoot)`, same as `refine/context.ts` already does. (Noted in `project_pause_state.md#1b`.)

### 7.2 Outputs testgen writes

Currently: `tests/integration/story-N.test.ts` only.

After: for each route/module covered by the spec, write both:
- `tests/integration/story-N.test.ts` — tier-1 tests
- `src/<path>/route.ts` (or similar) — stub

Testgen must detect whether a stub is needed:
- If `src/<path>/route.ts` already exists and has the right exports → skip the stub. (Brownfield consumers may already have handlers.)
- If not → write the stub.

### 7.3 Testgen prompt changes

Update `TESTGEN_SYSTEM` (packages/cli/src/commands/testgen/prompts.ts) with the tier-1 shape and the mock-helper conventions. Key additions:

- Tests MUST import the handler directly, not hit HTTP.
- Tests MUST mock external services via the per-project helper functions (e.g., `mockSupabase`, `mockResend`), NOT via inline `vi.mock({ from: vi.fn()...})`. This is load-bearing for the future fixture-based replay swap — see §4.3.
- If a required helper doesn't exist in the target project, testgen writes a minimal initial version of it to `tests/helpers/mocks/<service>.ts` alongside the test, same "stub" treatment as `src/` route stubs (§5). The PR body lists all helpers created.
- Helper signatures should accept a single intent-level options object; generated tests call them with the minimum data to express the test's intent, not with fully-assembled response trees.
- Each test starts with `resetMocks()` in `beforeEach` to avoid cross-test leakage.

## 8. Migration path for existing rewo stories

rewo currently has three testgen'd story files: 001, 003, 004. All are HTTP-loopback. After 0.7 ships:

1. Move current `tests/integration/story-00{1,3,4}.test.ts` → `tests/acceptance/`. Keep as-is; they'll run under `ACCEPTANCE=1` once tier-2 discovery lands.
2. Re-run testgen for each story under the new shape: `slowcook testgen --story 001 --force`. Output is new tier-1 tests + stubs.
3. Re-trigger brew on story-003 (the most backend-shaped) as the first real end-to-end validation.

Success metric: a brew run that produces **at least one checkpoint commit** within the budget. That's the bar — we don't need an all-green first run. Just proof that the ratchet can advance at all.

### 9.4 Phase D — tier-2 runner + recorder (later)

Out of scope for 0.7. Sketched here so we don't drift:

- **Discovery.** Extend `packages/stack-ts/src/discover.ts` to know about `tests/acceptance/`.
- **Runner.** Gate by `ACCEPTANCE=1`. Spawn `supabase start` + `next dev` in the test harness.
- **Recorder.** Wrap each external-service client with a record shim. Every `request → response` is scrubbed and written to `tests/fixtures/<story-id>/<service>/<hash>.json`. Scrubber has its own test suite; CI refuses to accept a PR with un-scrubbed fixtures.
- **Replay.** The tier-1 helper functions shipped in 0.7 (e.g. `mockSupabase(...)`) gain a fixture-backed mode. `resetMocks()` keeps working. Tier-1 tests are not rewritten — helpers just get smarter.
- **Staleness gate.** CI step that fails if any fixture under `tests/fixtures/` hasn't been re-recorded in N days (default 14), unless the story carries a `@fixtures-frozen` marker (e.g., for endpoints that don't change).
- **Workflow.** New GH Actions workflow `slowcook-acceptance.yml`, scheduled nightly + on-demand.
- Probably ships as **0.9.0**, after Playwright adapter lands.

## 10. Risks & open questions

**Mock drift.** Tier-1 mocks are load-bearing fictions. Supabase changes an API shape → tier-1 doesn't notice → tier-2 nightly fails → fix within 24 h. Manageable. The risk is acute only if tier-2 doesn't land soon after 0.7.

**Stub authorship quality.** If testgen's stubs have wrong signatures, tier-1 collection fails and brewing halts as TEST_RUNNER_BROKEN with no useful signal. Mitigation: testgen runs `tsc --noEmit` before committing the PR to prove stubs + tests type-check as a unit.

**Reviewer confusion.** Human approving the testgen PR sees both tests AND `src/` files. PR body must make the stub boundary explicit — include an "accepted stubs" section listing every generated file, with reviewer guidance: *"these stubs will be replaced by brewing; reject this PR only if the stubs' signatures or locations are wrong."*

**Consumer overrides.** A consumer might have project-specific mock patterns that differ from slowcook's defaults (e.g. a factory helper instead of inline `vi.mock`). `.brewing/context.md` is the escape hatch — that's why Phase A ships first.

**Brownfield stories.** If `src/<path>/route.ts` already has a handler and testgen detects it, what happens? Two sub-cases:
- Handler is full impl → no stub written. Tests fail against real behaviour → brewing edits the real handler.
- Handler is a stub from a previous testgen run → re-generate.

Decision: testgen always checks for the `@slowcook-stub` marker. If present → treat as "re-generate stub." If absent → assume real code, no stub, just tests.

**Test-bloat.** Tier-1 tests are more detailed than tier-2 because the mocks have to be explicit. A 10-assertion spec becomes a 200-line test file. Acceptable — that verbosity is the price of being able to ratchet.
