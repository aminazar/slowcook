# 0.15 — `plate` + `brew`: parallel-then-converge UI pipeline

> Status: drafted 2026-04-26 from a session conversation. Replaces 0.14 α.6→α.8 (refine emits mockup, then standard brew). The architectural change: insert a new `plate` agent before `brew` so the mockup (not the test prose) is the canonical target image. Today's `brew` keeps its name + role as the test-reconciliation step — the only change for `brew` is that on UI stories it now starts from `plate`'s code rather than empty stubs.

## Why

Today's pipeline asks `brew` to invent design from test prose. Test prose is not a design language; the failure mode is well-documented (see `feedback_soft_steering_vs_hard_signals`, `project_styling_gap_in_pipeline`, `project_page_integration_gap_in_tier1`). The escape from this slippery slope is to give the agent a *target image* — not just a target test.

Validated empirically on rewo PR #142 (story-016 brew): brew satisfied 26 green tests with a structurally wrong implementation (duplicated reaction cards, non-functional Pin button, affordance split from content). Tests measured what they could measure (handler shapes, axe, presence) and missed the UX that a human eyeballs in five seconds.

The fix is not to write more tests. It is to make the agent that produces UI work from a thing it can *see* (a running mockup), and let the test agent (`recipe`) write tests against that real thing rather than against an imagined design.

## Pipeline shape

```
human spec ─┬─ refine → spec.yaml ─────────────────────┐
            │                                          ▼
            └─ vibe → mockup → PM feedback → plate → recipe (reads plate's PR + spec) → tests
                                                ↓                                        ↓
                                                          brew ← ← ← ← ← ← ← ← ← ← ← ← ┘
                                                            ↓
                                                       served (final PR, tests green)
```

### Agents

- **`refine`** — *unchanged.* Writes the formal spec (invariants, api_contract, non_goals, proposals.schema/auth/etc). Runs in parallel with `vibe` from the same human input. Does not generate UI code.
- **`vibe`** — *new.* Reads the human spec + brownfield extracts (`schema.mmd`, `tokens.md`) + similar-pages-in-codebase hints. Output: `src/**/page.tsx` + components + `src/lib/data/<domain>.mock.ts` (the data-layer seam). Mock data only, no API integration. No correctness commitment, no tests target. Optimizes for "ship something runnable that looks right."
- **`plate`** — *new.* Manages PM iteration on vibe's mockup. PM reviews the running preview, comments + annotates screenshots; `plate` reads the feedback (vision-capable LLM) and amends the mockup. Same `/refine`-style loop pattern as today's spec amendments. When PM approves, `plate` writes the final mockup to a real branch + opens a PR labeled `slowcook-mockup`.
- **`recipe`** — *same agent as today, runs LATER in the new flow.* Reads BOTH plate's merged PR AND refine's spec. Writes tests against the actual rendered DOM (component names, hooks, event paths) informed by spec invariants. This kills the "tests for components that don't exist yet" guesswork that produces today's wrong-design failures.
- **`brew`** — *same agent as today, with new behavior on the UI path.* For non-UI stories (backend-only, infra), brew works exactly as it does today — write implementation from empty stubs to satisfy tests. For UI stories on the plate track, brew sees plate's complete-looking implementation as its starting code, with a system-prompt addition: "tests are red because the mockup uses mock data; replace mock data layer with real fetches; honor api_contract; do NOT redesign components." Reward function on UI stories = tests green with minimum edit distance from plate's PR.
- **`served`** — *not an agent, a label.* Marks the final brew-merged PR (tests green + based on plate's design).

The `plate + brew` path activates for stories with a UI surface (presence of `proposals.fixtures` in the spec is the trigger). Backend-only stories skip plate entirely and brew runs in its today-equivalent mode. `sift` (bug-flow) is unchanged.

### File-layout responsibility

```
specs/story-N.yaml                  ← refine writes (spec contract)
src/**/page.tsx                     ← vibe writes, plate amends, brew leaves alone
src/components/**                   ← vibe writes, plate amends, brew leaves alone
src/lib/data/<domain>.mock.ts       ← vibe writes, plate amends, brew leaves alone
src/lib/data/<domain>.ts            ← vibe writes (stub re-export), brew REPLACES with real fetches
src/app/api/**                      ← brew writes (handlers from api_contract)
supabase/migrations/*.sql           ← brew writes (from approved proposals.schema)
tests/integration/story-N.test.ts   ← recipe writes
tests/integration/story-N-ui.test.tsx ← recipe writes
```

`plate`'s allowed_paths: `src/**/*.tsx`, `src/components/**`, `src/lib/data/<domain>.mock.ts`. PM-iteration only.
`brew`'s allowed_paths: `src/lib/data/<domain>.ts`, `src/app/api/**`, `supabase/migrations/**`. Implementation only.

The seam between them is the `@slowcook-stub` marker on `<domain>.ts` (already shipped 0.14 α.2). Brew detects + replaces; plate doesn't touch the stub side.

## Why this beats today's pipeline

1. **Mockup is the target image.** The failure mode of today's brew is "satisfies tests with wrong design" because it has no image to check against. Plate makes the image canonical; brew can't drift from it.
2. **Tests written against real code, not imagined code.** Recipe sees the DOM that plate actually produced. Tests for `<RewoCard>` only get written if `<RewoCard>` exists in plate's PR.
3. **PM common sense enters early via mockup, not via test prose.** The slippery slope of tightening test specs is short-circuited.
4. **Two narrower agents instead of one wide one.** Plate optimizes for design, brew for correctness-with-minimal-diff. Each prompt is shorter, cheaper, and harder to mis-optimize.
5. **Parallel tracks reduce wall time.** Refine and vibe run in parallel from the same human input. Recipe waits for both; brew waits for recipe.

### Three layers of defense against "brew duplicates plate's UI"

The rewo PR #142 case study (story-016 brew, 2026-04-26) is the failure mode this plan most needs to prevent. What happened: brew was given a stub component path by testgen + a test that asserted "PinnedRewosStrip exists." The existing `/u/<handle>` page already rendered reactions correctly via `MemberReactionsPage` → `RewoCard`. Brew took the path of least resistance — flesh out the new stub component, render it alongside the existing one, leave the working component untouched. Result: two renderings of the same data, both green-tested but structurally wrong.

0.15 prevents this with three layers, only the last of which is a prompt:

**Layer 1 (hard, mechanical): `brew --mode plate` allowed_paths excludes UI.**

```
brew --mode plate can edit:
  src/lib/data/<domain>.ts        ← replace stub with real fetches
  src/app/api/**                  ← handler implementation
  supabase/migrations/**          ← schema migration

brew --mode plate CANNOT edit:
  src/**/*.tsx                    ← pages frozen
  src/components/**               ← components frozen
  src/lib/data/<domain>.mock.ts   ← fixtures frozen
```

The existing frozen-paths guard rejects commits that touch frozen paths. Brew physically cannot create or modify a UI file. If the diff requires it, brew halts with `MOCKUP_DESIGN_CONFLICT`.

**Layer 2 (hard, structural): recipe writes tests against plate's already-merged DOM, not against stubs.**

Today's testgen creates stub files at "the path the test will reference" — the stub IS the test scaffolding, and brew's job is to flesh it out. In 0.15, plate's PR is merged to main BEFORE recipe runs. Recipe imports components by their real path (`@/components/members/MemberReactionsPage`) because they exist on main. Recipe never references a path that doesn't exist, so brew never sees a "stub component to flesh out" affordance. The duplication path is closed because the affordance to "create new component to satisfy test" simply isn't there.

This is the load-bearing structural fix. Layer 1 is the safety net; Layer 2 means the safety net is rarely needed.

**Layer 3 (soft, prompt): recipe prefers behavior assertions over structure assertions.**

```
RECIPE_PLATE_MODE_ADDENDUM (added to existing RECIPE_SYSTEM when mode=plate):

Plate's PR has shipped src/**/page.tsx + components to main. Your tests
target the user-visible BEHAVIOR of those components, not their
implementation structure:

  PREFER (behavior): "owner sees a Pin/Pinned toggle on each reaction card"
  AVOID  (structure): "PinnedRewosStrip component exists at <stub-path>"

  PREFER (behavior): "clicking Pin POSTs to /api/pins; on 201 the strip
                       prepends the new pin"
  AVOID  (structure): "Pin button has onClick handler whose body matches
                       this regex"

Behavior assertions can be satisfied by ANY working implementation —
brew has the freedom to discover the data-layer fix that makes them green.
Structure assertions force a specific implementation, which removes
brew's freedom AND removes plate's redesign-on-iteration freedom (because
changing the component shape would break tests written against the
old shape).
```

**Why this combination works.** Layers 1+2 are mechanical: even an LLM optimizing pathologically for "tests green" can't satisfy them by duplicating UI. Layer 3 is the prompt-level steering that keeps recipe from writing tests that BACK brew into a corner where Layer 1 fires unnecessarily. The case study failure mode has no available path through any of the three.

## Open design questions

### 1. Conflict resolution when tests can't satisfy plate's design

Tests reflect spec invariants (correctness rules). Plate reflects design intent. When they conflict (e.g., spec says "no duplicate rendering" but plate ships duplicates), who wins?

**Proposal:** tests yield, brew halts, PM is notified with both diffs side-by-side. Don't auto-merge a fight. PM either (a) amends spec to relax the invariant, (b) re-iterates with plate to fix the design, or (c) accepts the conflict and merges manually.

### 2. Cost

Three LLM rounds (vibe + plate + brew) where today there are two (refine + brew). Per-round expectations:

- `vibe`: $0.50–$1.50 (one shot; broad scope but bounded; mostly file emission)
- `plate`: $0.30–$1 per iteration; usually 1–3 iterations before PM approves
- `brew`: $0.50–$2 (narrow ratchet; minimal edits; cheaper than today's brew because design is fixed)

Today's brew alone is $1–$3. So new total ≈ $1.30–$5.50 vs today's ≈ $1.30–$5. Roughly break-even. Plus `refine` cost on both (unchanged).

### 3. Vibe's input format

Issue body alone is underspecified. Vibe needs:
- The human spec (issue body).
- Brownfield extracts (`.brewing/diagrams/{schema.mmd, tokens.md}`).
- Component-vocabulary hints from `.brewing/code-map.json` (component names + paths).
- Optionally: "similar pages in codebase" — pointers to existing `/u/<handle>` if the new story is `/u/<handle>/pins`.

### 4. Where the mockup lives

`vibe` writes to a feature branch (`slowcook/mockup/story-N`). `plate` iterates on that branch. PM reviews via Cloudflare/Vercel preview deploy of the branch. Approved mockup is merged to main BEFORE recipe runs — so recipe + brew see the mockup as already-shipped code on main.

This is a departure from the current pattern where everything lives in flight on branches until brew finishes. The mockup-on-main pattern means even if `brew` halts, the design is reviewable in production.

### 5. Vibe vs plate split

Are these one agent in two phases or two distinct agents?

**Lean: two distinct agents with different system prompts.** Vibe's prompt is "ship a fresh mockup." Plate's prompt is "amend an existing mockup per PM feedback, preserving structure unless feedback explicitly changes it." Same shape as today's `refine` initial-emit vs amendment paths — works well there.

## Out of scope for 0.15

- **Multi-mockup variants.** PM picks one design at the plate step; no A/B-style mockup comparison. Could add later (`plate --variants 2`).
- **Mockup-driven testgen for non-UI stories.** Backend-only stories skip the plate track; brew runs in its today-equivalent mode.
- **`vibe` for fixing existing UI bugs.** That's the bug-flow's territory (`investigate → recipe --regression → sift`). Plate+brew is for new feature implementation.

## Implementation specifics

### CLI surface

Two new subcommands; one existing one extended.

```
slowcook vibe --spec <id> [--cwd <path>] [--owner <login>] [--repo <name>]
  Reads specs/story-<id>.yaml + brownfield extracts + code-map.
  Emits src/**/page.tsx + components + src/lib/data/<domain>.mock.ts to a
  new branch slowcook/mockup/story-<id>; opens PR labeled slowcook-mockup.
  No correctness gating; the PR's preview deploy is the review surface.

slowcook plate --pr <number> [--review-comment-id <id>]
  Mirror of `slowcook refine --pr` for the mockup branch. Reads PR
  comments + annotated screenshot attachments since last plate commit;
  amends the mockup files; force-pushes. Posts threaded reply to the
  triggering comment when --review-comment-id is set.

slowcook brew --story <id> [--mode plate|legacy] ...
  Existing command. New --mode flag (default: auto-detect from spec).
  --mode plate: starting state = plate's merged mockup; allowed_paths
    restricted to data layer + API + migrations + tests; system prompt
    augmented with "do not redesign components".
  --mode legacy: today's behavior unchanged; for backend-only stories
    or consumers that haven't opted into the plate track.
```

Auto-detection rule for `slowcook brew --story <id>`: if the spec has `proposals.fixtures.by_domain.*.seed` populated (non-empty) AND a `slowcook-mockup` PR has merged for this story, mode = `plate`. Otherwise mode = `legacy`.

### System prompt skeletons

**`VIBE_SYSTEM`** (lives in `packages/llm-anthropic/src/prompts/vibe.ts`):

> You are vibe — slowcook's design-first mockup agent for the slowcook brewing harness.
>
> Your job: read a spec + the project's brownfield extracts + code-map, and emit a runnable React mockup that demonstrates the spec's UI behavior using mock data.
>
> ## Project context (brownfield)
> ${projectContext}  ← schema.mmd, tokens.md, code-map summary, similar pages
>
> ## What to emit
> - One or more `src/**/page.tsx` files for the routes the spec implies
> - Components under `src/components/...` following existing folder conventions
> - `src/lib/data/<domain>.mock.ts` files with hand-authored fixtures matching `proposals.fixtures.by_domain[domain].seed`. If seed is empty, populate it with 3-5 realistic rows yourself.
> - `src/lib/data/<domain>.ts` re-export stubs with the `@slowcook-stub` marker (brew will replace).
>
> ## Hard rules
> - All visible color/spacing comes from existing tokens (cite by name from tokens.md). NEVER use raw hex/rgb except in CSS files. Use Tailwind classes that map to project tokens.
> - All components reference real existing primitives by import path when applicable (cite paths from code-map).
> - Click handlers MUST work (state changes locally via React state) even though data is mock — the PM will click through.
> - No real API calls. The data layer goes through `src/lib/data/<domain>` only.
> - No tests. recipe will write tests against your DOM later.
>
> ## Output format
> [structured emit-block with file paths + contents, similar to brew's edit_file tool calls]

**`PLATE_AMENDMENT_SYSTEM`** (lives in `packages/llm-anthropic/src/prompts/plate.ts`):

> You are plate — slowcook's mockup-amendment agent. The PM is reviewing a running preview of a mockup vibe emitted; you receive their feedback and amend the mockup files.
>
> ## Spec
> ${spec}
>
> ## Current mockup state
> ${listOfMockupFiles + theirContents}
>
> ## PM feedback since last commit
> ${reviewComments + annotatedScreenshots}  ← screenshots come as image messages
>
> ## Your job
> - Read every feedback item; categorize as: visual change / behavior change / structural change.
> - Amend the minimum set of files necessary. Preserve unrelated structure.
> - When feedback is ambiguous, make your best interpretation and note it in the PR reply.
>
> ## Hard rules
> - Tokens + components from existing project vocabulary only (same as vibe).
> - Don't touch `<domain>.ts` stubs; only `<domain>.mock.ts` + `page.tsx` + components.
> - Output a summary comment for the PR explaining what changed per feedback item.

**`BREW_PLATE_MODE_ADDENDUM`** (added to existing `BREW_SYSTEM` when mode=plate):

> ## Plate-mode constraints (this story has a PM-approved mockup on main)
>
> The `src/**/page.tsx`, `src/components/**`, and `src/lib/data/<domain>.mock.ts` files are CURRENTLY ON MAIN — committed by plate after PM approval. Treat them as frozen design.
>
> Your job is to make the failing tests pass by:
> 1. Replacing `src/lib/data/<domain>.ts` (currently re-exports from .mock.ts) with real fetches against the API. Honor `api_contract` for endpoint paths + response shapes.
> 2. Implementing `src/app/api/**` route handlers from `api_contract`.
> 3. Writing migrations under `supabase/migrations/` from `proposals.schema.sql` (must be `status: approved`).
>
> You MUST NOT edit:
> - `src/**/page.tsx`
> - `src/components/**`
> - `src/lib/data/<domain>.mock.ts`
> - The mockup is the design contract. If a test cannot be satisfied without changing the mockup, halt with `MOCKUP_DESIGN_CONFLICT` and the PM will resolve.

### Branch + PR flow

```
issue → refine → specs/story-N.yaml on slowcook/spec/story-N branch (existing)
       \ vibe → src/**/...mockup files on slowcook/mockup/story-N branch [NEW]
                                       │
                  PM iterates ←──────── │ (plate workflow on PR comments)
                                       ▼
                    PM merges slowcook-mockup PR (mockup is on main)
                                       │
                                       ▼
                  recipe fires (existing on-spec-merged + on-mockup-merged) → tests PR
                                       │
                          PM merges slowcook-tests PR
                                       │
                                       ▼
                  brew --mode plate fires (auto-detected)
                                       │
                                       ▼
                       slowcook-brew PR (data layer + API + migrations)
                                       │
                          PM merges → "served" final state
```

Two new workflow files in `packages/forge-github/src/templates.ts`:

- `slowcook-vibe.yml` — fires on spec-merged WHEN `specs/story-N.yaml` has `proposals.fixtures.by_domain` populated AND no `slowcook/mockup/story-N` branch exists yet.
- `slowcook-plate.yml` — fires on `pull_request_review_comment` / `issue_comment` / `pull_request_review` matching `/plate` on a PR labeled `slowcook-mockup`.
- Modify existing `slowcook-tests-merged.yml` (or `slowcook-mockup-merged.yml` new): when `slowcook-mockup` PR merges, trigger `slowcook recipe --story N` (which already runs from a merged spec; just needs to wait for both spec AND mockup before firing).
- Modify existing `slowcook-brew-auto.yml`: when `slowcook-tests` PR merges AND a `slowcook-mockup` PR is also merged for the same story, dispatch `slowcook brew --story N --mode plate`.

### Spec.proposals mutations during the pipeline

| Stage | Mutates | How |
|---|---|---|
| refine emit | proposals.* status: pending | Initial emit |
| vibe emit | proposals.fixtures.by_domain.*.seed | Populates with 3-5 realistic rows if seed was empty (synth shell) |
| plate amend | proposals.fixtures.by_domain.*.seed | Adjusts seed to match mockup behavior under PM iteration |
| plate approve | proposals.ui_layout.status: approved | When PM merges slowcook-mockup PR, `slowcook-mockup-merged` workflow flips status |
| brew | proposals.schema.status: approved | Brew opens migration file → on-brew-merged workflow flips schema status |

The pipeline never overwrites a `proposals.*.status: rejected` automatically — PM must manually flip back to pending or approved.

### Conflict resolution: `MOCKUP_DESIGN_CONFLICT` halt

When brew (--mode plate) finds it cannot satisfy a failing test without editing a frozen plate file, it halts with class `MOCKUP_DESIGN_CONFLICT`. The halt comment includes:

- The failing test name + assertion
- The frozen file brew would have needed to edit
- Two side-by-side diffs the PM can pick from: (a) "what the test wants" pseudo-implementation; (b) "what plate's design implies" interpretation
- Three resolutions the PM can take:
  - Comment `/plate <prose>` on the slowcook-mockup PR's source (plate amends the mockup; brew re-runs)
  - Comment `/refine <prose>` on the spec PR (refine relaxes the invariant; testgen/recipe re-emits; brew re-runs)
  - Manually edit the brew PR + merge with admin override (PM accepts the conflict)

Same shape as today's brew halt classes; new class added to `core`'s halt schema enum.
