# 0.16 — Singular mock app + element-anchored review

> Status: drafted 2026-04-27, updated 2026-04-26. Architectural reset of 0.15 (which mixed mock data into `src/` via a data-layer seam). 0.16 separates mock + production into two filesystems, makes the mock a real runnable docker-deployable artifact, and routes PM feedback through an element-anchored overlay.
>
> Current state (2026-04-26): α.1 + α.2 + α.3 + α.4 are shipped (mock-runtime package + Scenario types in core + `slowcook init mock` CLI + BUG-F refine-synth fixes + vibe v2 + recipe-blind-to-mock testgen tweak). α.5–α.10 is the open road.

## Why

0.15 made three mistakes:

1. **Mock data colocated with production** (`src/lib/data/<domain>.{mock.ts,ts}`). One bad import + mocks ship to prod. PMs reviewing the mock had to checkout the branch + run `npm run dev` locally — no live preview infrastructure.
2. **Per-story mocks** — every story added shadow components alongside production primitives, which let brew duplicate UI to satisfy stub-path tests (the rewo PR #117 + #142 failure mode).
3. **Brew did everything** — vibe wrote mockup files; brew swapped data layer + dealt with whatever drift PR comments caused. Brew's reward function (test-pass) doesn't include "looks right" so the design contract was always at risk.

0.16 fixes all three structurally.

### Concurrency rule for the parallel branch

After spec-merge, the same workflow event fires both `slowcook-vibe.yml` and `slowcook-testgen.yml`. They write into separate filesystems (`mock/` vs `tests/`) so their PRs can be merged in any order. `slowcook port` waits for both before firing brew — the orchestration workflow checks "both labels (slowcook-mockup AND slowcook-tests) merged into main for this story-N" before dispatching.

## Architectural rules

These are load-bearing. Every implementation decision in 0.16-α.* must respect them.

1. **Mock + production are SEPARATE filesystems.** `mock/` and `src/`. No file lives in both; no file imports across the boundary. The `slowcook port` step is the ONLY direction code flows: mock → src.
2. **Mock is UI-only.** No Supabase, no `fetch()`, no API of any kind. Scenarios are plain TypeScript modules; React hooks read them; mutations are local component state. Refresh resets state — that's correct mockup behavior.
3. **Mock is singular and grows incrementally.** One `mock/` directory per consumer; new stories add scenarios to it; rarely add components. No per-story shadow copies; no `*Mock`-suffixed components.
4. **Vibe and recipe are BLIND to each other.** Two independent interpretations of the same spec. Vibe writes mock; recipe writes tests. They never read each other's output. Brew is the reconciliation point.
5. **Brew never copies, never UI.** `slowcook port` is the deterministic copy step. Brew's LLM work is pure backend wiring + test-passing iteration. Same agent shape as today's brew with a narrower allowed-paths.
6. **Slowcook owns the runtime; consumer owns the shell.** `@slowcook-ai/mock-runtime` ships scenario types, hooks, registry, ScenarioPicker. `slowcook init mock` scaffolds the consumer-side shell (~12 customizable files). Runtime updates flow via `npm bump`; shell stays put.
7. **Slowcook is stateless re: hosting.** Each consumer provides their own SSH-reachable box (Docker + reverse proxy). Slowcook ships CI tooling that scp + ssh + `docker run` on that box. We never host anything for anyone.
8. **Element-anchored comments are real artifacts.** Overlay POSTs structured payload to the PR (selector + screenshot region + viewport + OS + prose). Plate parses the JSON. The full thread (PM comment → plate amendment) is the audit trail + training material.
9. **Approval is explicit.** PM clicks an approve toggle on the overlay → posts an approval comment + adds `slowcook-mockup-approved` label. Plate refuses to amend after approval (so a stray PM comment doesn't bounce a finalized mockup).
10. **Tech stack matches between mock and production.** Same framework (Next.js + React for rewo). Cross-stack mocking deferred indefinitely.

## Per-agent roles

### `refine` (unchanged)

Writes `specs/story-N.yaml`. Does not generate UI. Doesn't change for 0.16.

### `vibe` (rewritten in α.4)

Reads:
- `specs/story-N.yaml`
- existing `mock/` (entire app) so it can extend rather than duplicate
- brownfield extracts (`.brewing/diagrams/{schema.mmd, tokens.md}`)
- code map summary

Writes:
- `mock/scenarios/story-N.ts` (always)
- `mock/src/components/<group>/<NewComponent>.tsx` (only when a new UI primitive is needed and no existing one fits)
- One new line in `mock/src/lib/scenario-registry.ts`'s import block + one new entry in the `defineScenarios([...])` array

System prompt rules:
- REUSE existing mock components by import path. Cite the path.
- REUSE existing tokens by name (from tokens.md).
- Click handlers must work locally (`useState` + scenario fixtures).
- NO real API calls.
- NO test files.
- Surface a `<component_change_request>` block when an existing primitive needs a new prop — do not fork.

Output PR labeled `slowcook-mockup`.

### `plate` (rewritten in α.7)

Triggered by PR review-comments matching `/plate` OR by any element-anchored comment via the review-overlay (which posts a comment with hidden JSON the plate workflow recognizes).

Reads:
- spec.yaml (for cross-checking comments against spec assertions)
- mockup branch's current files
- All unresolved PM comments since the last plate commit
  - timeline (prose)
  - inline review (anchored to a file:line)
  - element-anchored (anchored to DOM element with screenshot + viewport)

Per-comment classification (NEW in 0.16):
1. **Cosmetic** → amend mock with minimum diff
2. **Spec-altering** → ESCALATE: "this would change spec assertion X + invalidate test T; confirm?". Wait for PM response (via /plate confirm-spec-change OR /plate keep-spec OR /plate discard).
3. **Mock-divergence** → amend mock to align with spec, note in summary why the original PM ask was rejected.

After amendment: force-push mockup branch; post `<plate_summary>` PR reply listing each feedback item + the action taken.

Refuses to amend after `slowcook-mockup-approved` label is set.

### `recipe` (small prompt tweak in α.4)

Unchanged operationally — already runs on spec-merge, writes tier-1 tests. The only change: prompt steers strongly toward **behavior assertions** (`screen.getByRole("button", { name: /pin/i })`) and away from **component-name imports**. Tests render the page entry point with mockSupabase + assert behavior. No coupling to specific component file paths.

Stays blind to mock — never reads mock/ files.

### `slowcook port` (NEW deterministic step in α.8)

CLI command, no LLM. Runs as a CI step before brew.

```
slowcook port --story N
  Reads:  mock/src/components/* + mock/src/app/*
  Writes: src/components/* + src/app/* (mirroring paths)
  Rewrites: imports of @slowcook-ai/mock-runtime hooks → real
            hooks against the production data layer
  Excludes: mock/scenarios/, mock/lib/scenario-registry.ts, mock/data/,
            anything that's mock-only infrastructure
```

Pure scripting. Same input → same output. Auditable diff in the brew PR.

### `brew --mode plate` (rewritten in α.9)

Reads:
- spec + ported src/ (UI already in place)
- recipe-written tests (red)
- mock/ as visual reference

Writes:
- `src/lib/data/*` — real Supabase queries returning shapes matching what ported components expect
- `src/app/api/*` — handlers per api_contract
- `supabase/migrations/*` — per proposals.schema (status: approved)

Allowed-paths: `src/lib/data/**`, `src/app/api/**`, `supabase/migrations/**`, `tests/**` (only for fixing flaky tests; usually untouched).

Frozen-paths: `src/**/*.tsx`, `src/components/**` — physically rejected by the guard.

Halt class: `SPEC_AMBIGUITY_DETECTED` — when test demands X but rendered DOM shows Y. PM resolves via `/plate` (amend mock to satisfy test) OR `/refine` (relax spec invariant) OR manual override-merge.

## File-layout responsibility

```
specs/story-N.yaml                   ← refine writes; never touched again
tests/integration/story-N*.test.ts   ← recipe writes; brew reads (red) + iterates
mock/                                ← vibe + plate write; brew NEVER touches
  package.json, Dockerfile, etc.     (consumer-owned shell, scaffolded by `slowcook init mock`)
  src/app/, src/components/          (vibe extends; plate amends per PM feedback)
  src/lib/scenario-registry.ts       (vibe extends — one new entry per story)
  scenarios/story-N.ts               (vibe writes; plate amends; one per scenario)
  data/                              (shared fixtures: users, rewos, etc. — vibe/plate maintain)
src/                                 ← `slowcook port` copies here from mock/
  app/, components/                  (UI; brew NEVER edits, frozen-paths guard rejects)
  lib/data/                          (data layer; brew writes real Supabase queries)
  app/api/                           (handlers; brew writes per api_contract)
supabase/migrations/                 ← brew writes per proposals.schema
```

## Element-anchored review overlay (α.6)

Per [`0.13.1-review-overlay.md`](./0.13.1-review-overlay.md) — design preserved, ships as `@slowcook-ai/review-overlay`. Key bits:

- **Floating toggle** persistently visible (top-right desktop, bottom-right mobile)
- **Three modes** (extending the original two-mode design):
  - **Nav** (default) — all interactions normal
  - **Comment** — crosshair cursor; click captures element + opens comment composer
  - **Approve** — single-click commits the slowcook-mockup-approved label + posts approval comment
- **Comment composer** captures:
  - Element selector (id > data-testid > role+name > tag.classes:nth-child > XPath fallback)
  - Screenshot of the element region (canvas API)
  - Optional uploaded screenshot (PM-annotated)
  - Optional browser recording (MediaRecorder API → webm; ship later)
  - Viewport dimensions (auto)
  - OS + browser version (auto, navigator.userAgent)
  - URL at time of comment (auto, includes ?scenario=)
  - Timestamp (auto)
  - Prose
- **Submit path**: PM provides a GitHub PAT once, stored in localStorage for the preview domain. POST to `/repos/{owner}/{repo}/issues/{pr_number}/comments` with rendered markdown body + hidden JSON payload.
- **Plate parser** extracts the hidden JSON from comment bodies, classifies, amends.

## Bug-flow + mock (future consideration)

When `investigate` diagnoses a production bug, the root cause may be:

- **(a) Production diverged from mock** — fix in src via sift; standard bug-flow.
- **(b) Mock has the wrong design** — PM-approved mockup encoded a UX bug. Fix in mock via plate iteration; then re-port via brew.

Investigate's output schema will distinguish these (`root_cause: "production-divergence" | "mock-design-issue"`). Detail deferred to 0.16-α.10+ (out of scope for the initial 0.16 cut).

## SSH preview deploy (α.5)

Slowcook ships:

- `slowcook preview deploy --pr <n>` CLI command (runs in CI)
- `slowcook preview teardown --pr <n>` CLI command (runs on PR close)
- `slowcook-preview-deploy.yml` + `slowcook-preview-teardown.yml` workflow templates
- `docs/operating-guide.md` covering box setup (Docker + reverse proxy + SSH user + wildcard cert)

Consumer `.brewing/preview.yaml`:

```yaml
preview:
  type: ssh
  host: preview.rewo.app
  user: slowcook-deploy
  key_secret: SLOWCOOK_PREVIEW_SSH_KEY      # GitHub Actions secret name
  port_range: [4000, 4099]
  url_template: "https://mock-{port}.preview.rewo.app"
  remote_root: /opt/slowcook-preview
```

CI flow per `slowcook preview deploy`:

1. `cd mock && npm ci && npm run build`
2. `tar czf /tmp/mock-pr-N.tgz .next public package.json`
3. `scp /tmp/mock-pr-N.tgz $user@$host:$remote_root/pr-N/`
4. `ssh $user@$host` — pick free port from range; `docker run -d --name mock-pr-N -p $PORT:3100 slowcook-mock-runtime`
5. `gh pr comment $PR_NUMBER --body "Preview ready: $url"`

Box-side requirements (consumer documents these in their ops):

- Docker engine + deploy user in docker group
- Reverse proxy with wildcard subdomain cert (Caddy easiest; auto-Let's Encrypt)
- `~slowcook-deploy/.ssh/authorized_keys` matches the GitHub secret's private key
- `$remote_root` writable by deploy user
